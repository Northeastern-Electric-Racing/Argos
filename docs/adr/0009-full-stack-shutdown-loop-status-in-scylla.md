# Work out the shutdown loop status in scylla too, and publish it as datapoints and Faults

scylla-server works out the Shutdown Loop page's status itself, with the same algorithm as the angular-client, and publishes it as `Argos/Shutdown/*` datapoints through the same channels MQTT data takes: the socket channel (clients, Rules, the Fault list) and the database channel (stored with the current Run). Loop openings, mismatches and CAN latch trips that hold are raised as Faults on the `Vcu` or `Bms` Node. The page prefers scylla's node states while they are fresh and falls back to computing locally. Topics, codes and Fault names are in `docs/spec/shutdown-loop-page/spec.md` (Data). No database migration is needed.

## Considered Options

- **Frontend only** (the spec's first draft). Rejected: a trip seen by nobody is lost, there is no history to ask "why did the car shut down on lap 7?", and Rules can't watch the loop.
- **A REST endpoint or socket event for the status.** Rejected: neither is stored, so no history, and Rules only see datapoints.
- **A table in the argos database (ADR 0008).** Rejected: needs migrations and its own history queries, and Rules, the graph page and Grafana already work on datapoints. The status is a function of car data in a Run, float-valued, so it fits a datapoint.
- **Compute inside the socket handler, beside `Argos/Message_Rate`.** Rejected: that handler is off with `--no-metadata` and already large. A task of its own, like the track handler, publishes into the shared channels and stays testable.
- **Only the server computes; the client just displays.** Rejected for now: the client already receives every reading through scylla, so this is not about offline use, but the page would go blank against a scylla without the task (older images), the dev mock panel publishes only into the client, and a client copy keeps the page usable while the server output is missing. The cost is two copies, guarded by golden vectors. Nero cannot use either copy: scylla's output goes to its socket, not to Siren.
- **One shared JSON loop definition read by both.** Rejected: each component builds in its own Docker context (`angular-client/`, `scylla-server/`), so a file outside one isn't there at build time. scylla keeps its own table (`shutdown_loop/model.rs`), and a `cargo test` reads the client's `shutdown-loop.model.ts` and `shutdown-page.topics.ts` and fails if the order, topics, boards, `openOnly` flags or critical faults differ.

## Why this shape

- **History and Rules for free.** Stored datapoints carry the Run, so the graph page and Grafana show when and where the loop opened, and a Rule like `a < 0.5` on `Argos/Shutdown/Verdict` can notify the pit (Rule values are floats: compare with `a < 0.5` or a float literal such as `0.0`, never an integer literal like `0`).
- **Same path as car data.** Publishing into the socket and database broadcasts means the socket handler, rule engine, track handler and batch upsert treat the status like any topic. The task ignores `Argos/Shutdown/*`, so it never reads its own output.
- **One evaluation per burst.** The car publishes each signal of a CAN frame as its own message, so scylla evaluates 25 ms after the first input of a burst (later inputs don't push that back), never on a half-applied frame. It also evaluates at the next staleness, grace or hold deadline, and on a 1 s heartbeat while any input is live.
- **Faults through the existing Fault list.** scylla publishes `Argos/Shutdown/Fault/{Vcu|Bms}/{name}` as 1 every second while active and 0 once when it clears. The socket handler turns 1 into an occurrence (first occurrence, last seen) and 0 into expired, so the Fault ends when the loop closes, not when an unrelated message arrives. While the verdict is Unknown, Faults are held, not refreshed, until their board reads again, so a dropout doesn't look like a recovery. A Fault that comes back within 8 s of clearing reopens its entry.
- **Times.** Staleness and grace windows use when scylla received each message, on a monotonic clock, never the car's clock, which can be off. The published datapoints carry the car's timestamp of the input that produced them, so they line up with the car data beside them; heartbeats carry that timestamp plus the time since scylla received it.
- **The client prefers the server only while it can trust it.** The server sees every message; a client may have some dropped by the socket discard setting, so scylla's own `Argos/Shutdown/*` datapoints are exempt from the socket discard. The client uses scylla's node states only if they arrived in the last 2 s and have one valid code per loop node; otherwise, and while the dev mock panel publishes, it computes locally.

## Consequences

- **Derived telemetry counts as car data.** ADR 0008 keeps Argos-only data out of the car database. `Argos/Shutdown/*`, like `Argos/Message`, is not Argos-only: it is a function of one Run's car data, has no meaning outside that Run, and must sit beside the readings for history, Grafana and Rules. It is stored in the car database and goes to the cloud with the rest of the Run. ADR 0008 is amended to say so.
- **Glossary.** `docs/CONTEXT.md` now lists `Vcu` as a Node, persisted derived topics under Topic, derived Faults under Fault, and **loop node**.
- **Two copies of the algorithm.** `shutdown-loop.utils.ts` and `scylla-server/src/shutdown_loop/status.rs` must change together. A `cargo test` checks the node table against the client's, and both test suites run the same golden vectors (`angular-client/src/pages/shutdown-page/shutdown-loop.vectors.json`), so a change to either algorithm fails until the other matches. Scylla CI runs when those client files change.
- **Which openings are Faults.** Operator switches are not Faults: an opening blamed only on the GLV master switch, TSMS or HVD is recorded in `Argos/Shutdown/Verdict` and `Break_Node` but raises no Fault; latches, kill buttons, interlocks, BOTS and the inertia switch do. The name follows the suspect stretch (`Shutdown_Open_SIDE_BRB_R_TO_BMS_LATCH`), not the reading that found it. A CAN latch trip raises only `CAN_Latch_<FAULT>` for each tripped critical fault. A Fault is raised only once it has held for 500 ms, and an opening only once the break's topic has reported again since it began (a cross-board break needs a fresh sample), so openings under 500 ms show in `Verdict`, `Break_Node` and on the page but are not Faults.
- **Extra data.** Five status datapoints per heartbeat while any input is live, plus one set per change burst, plus one per active Fault per second; nothing once every input is stale.
