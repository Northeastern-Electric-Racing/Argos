# Selective per-screen telemetry subscription over the existing Socket.IO transport

Argos replaces the Socket.IO firehose (every client receives every decoded topic — ~900 topics, ~2,900 msgs/s under sim load — and discards most of it) with server-mediated selective delivery on the same transport. The client sends one idempotent `set_subscriptions` control event carrying its full desired filter list (exact topics plus MQTT-style wildcards); scylla-server keeps a per-socket filter set and a memoized topic→sockets index (matcher = `rumqttc::mqttbytes::matches`, already in the dependency tree) rebuilt on any subscription change, and gates the `data` emit through that index. MQTT appears in this design as vocabulary only: topic names and wildcard syntax come from the car's existing ingest path (Calypso → Mosquitto → scylla), and the matcher is a single string-matching function from the MQTT client crate scylla already uses for that ingest. The browser-facing transport is Socket.IO alone — the browser never connects to a broker. Server-synthesized channels (runId enrichment, Viewers, Message_Rate, faults, timers, per-client rule notifications) are untouched — they ride the ungated `metadata` event or per-socket emits. No new processes, no new client dependencies. On the BMS page this cuts delivery from ~2,900 to ~510 msgs/s per client.

## Considered Options

1. **Replace-set control message over socketioxide** (chosen).
2. **Broker-direct MQTT over WebSocket** — browser subscribes Mosquitto directly and decodes protobuf.
3. **NATS side-car** — scylla republishes enriched JSON to a nats-server; browser subscribes via nats.ws.
4. Within Socket.IO: rooms and dynamic namespaces (dismissed — socketioxide has no connection-state recovery, so reconnect wipes membership either way; wildcards don't map to rooms). A wider 2026-07 survey (WAMP, STOMP, GraphQL subscriptions, raw axum WS, Centrifugo, Mercure, EMQX, Redis/Kafka) found nothing better at Argos scale (~15 pit-wall clients).

Options 1–3 were built as live spikes off a common baseline (local worktrees `spike-selective-subscription`, `spike-broker-direct-mqtt`, `spike-nats-delivery`; never pushed — results are summarized here) and measured head-to-head on the BMS page.

## Why the socket wins

- **Latency is a non-differentiator.** Measured with differential same-message matched pairs: one browser subscribed the identical topic set on both paths, deltas taken with a single `performance.now()` clock at WebSocket frame arrival (no cross-machine clock arithmetic), ~111k pairs per scenario at ~510 msgs/s, zero parse errors. MQTT-direct was −0.8 ms p50 vs the socket (it skips scylla entirely); NATS was +0.4 ms p50 (extra republish hop). Total spread across all three: ≈1.2 ms median, low-single-digit-ms tails. The UI Latency tile that previously suggested larger gaps computes `Date.now() − publisher_timestamp` across machines and is invalid.
- **Memory is a non-differentiator.** Four-minute soaks with forced-GC bracketing showed the same ~6–7 MB/min client heap retention on all three variants (a pre-existing BMS-page leak, ticketed separately); scylla RSS sat in the same band in all three; nats-server added a flat 16 MB process; the MQTT variant carried a +9 MB browser floor (mqtt.js + protobufjs lazy chunk, 104.5 kB gz).
- **Broker-direct MQTT is functionally degraded.** runId is injected by scylla post-ingest, so broker-delivered live data loses it; metadata, history, and rule notifications still need the socket, so it forces a permanent hybrid (adds a system, removes none); the browser needs a protobuf decoder. Exposing the broker to browsers is also safety-critical: the dev configuration's anonymous WebSocket listener accepts browser publishes to `Calypso/Bidir/*` car-actuation topics, so any production use would require broker authentication, ACLs, and TLS before a browser may ever connect.
- **NATS is the escape hatch, not the choice.** It keeps enrichment (runId present) and has protocol-native wildcards and auto-resubscribe, but adds a second broker to deploy and monitor while scylla remains the single point of failure anyway (it is the republisher), plus an always-serialize republish hop and a second live browser connection. It stays the designated migration path if socket fan-out ever becomes the bottleneck at 10–100× client counts.
- **Exactly-once by construction.** The server index delivers each message to each interested socket once. Broker paths must manage overlapping subscriptions themselves (the current client emits ~490 exact topics where one page wildcard would do, which produced duplicate delivery on NATS); the baseline is immune because subscription-set size is free in a server-side index.
- **Replace-set beats incremental deltas.** socketioxide does not implement connection-state recovery (upstream issue #729), so the client must re-declare interest on every connect regardless of mechanism. An idempotent full-set resend has no drift surface; subscribe/unsubscribe deltas would recreate one.

## Consequences

- scylla-server: new `socket_subscriptions.rs` (per-socket filter sets, firehose default set, memoized topic→sockets index) plus the handler and emit gate in `socket_handler.rs`. Fast paths: when all sockets are on firehose the broadcast is byte-identical to today; topics no socket watches skip serialization entirely. The wire stays replace-set (full state, self-healing) while the server applies each message by diffing the new list against the socket's previous set and patching the index incrementally (added/removed only, atomic swap) — delta efficiency without delta drift; a dirty-flag lazy rebuild backstops set-spamming clients.
- angular-client: refcounted storage service (`ReplaySubject(1)` per topic, ~5 s linger, existing `get()` signature unchanged, new `subscribe(filter)` wildcard API); desired-set changes are coalesced on a microtask at the end of the current task — a page mount's ~490 `get()` calls become one control message with zero added latency (no timer; background tabs throttle timers but not microtasks) — and the full set is resent on every `connect`.
- Rollout is screen-by-screen and reversible: a socket stays on firehose until its first `set_subscriptions`, so un-migrated screens and old client builds are unaffected (mixed-fleet compatibility was verified live against an unmodified production client image).
- The first `set_subscriptions` may ride the engine.io polling transport before the WebSocket upgrade — irrelevant to correctness, relevant to anyone debugging by sniffing WS frames.
- Follow-up work surfaced by the spikes, ticketed separately: the graph-page sidebar eagerly pins ~911 filters via per-tree-node `toSignal(storage.get(...))` in `tree.utils.ts` and needs lazy signal creation; the BMS page retains ~6–7 MB/min regardless of transport (suspects: the pre-existing NG0100 mutation storm and never-torn-down CellService subscriptions); the Latency tile should be replaced by the server-side latency publisher already present but commented out in `mqtt_processor.rs`.
- Test-infra fixes made during the spike (spec tsconfig node types, karma zone.js polyfills, graph-page spec type error) apply to develop regardless of this decision.
